Privacy policy

This policy covers the ReproParcel project website and the open-source SDK distribution. It does not cover an application that integrates ReproParcel — that application's developer is responsible for its own disclosures.

Effective: 12 November 2026Last updated: 12 November 2026Status: pre-release

i

In one paragraph. This website sets no cookies, runs no analytics and makes no third-party requests. The project operates no server that receives report data. The SDK starts with collection disabled, and a host application decides — with its own policy and its own disclosures — whether any evidence is captured. When evidence is captured, it stays on the user's device until the user chooses to export or share it.

1. Scope

This policy applies to:

  • this project website, including every page under this domain path;
  • the ReproParcel source repository, release artifacts and documentation we publish;
  • the open-source SDK modules, desktop tools and reference implementations distributed by the project.

It does not apply to a host application that integrates ReproParcel, to a downstream fork, to a self-hosted relay deployed by someone else, or to any third-party service you reach through a link. Those are controlled by their own operators.

2. This website

The site is a set of static files. It runs no server-side application logic of its own.

GitHub, as the hosting provider, may process standard technical request data — such as an IP address, user agent and requested path — under the GitHub Privacy Statement. That processing happens at the host, not in the project's software, and the project does not operate an analytics pipeline over it.

3. The ReproParcel SDK

The SDK is a library embedded in a host Android application. The project does not receive SDK data. There is no project-operated collection endpoint, no account system and no default upload.

3.1 Collection is off by default

Installing the library starts no collection. A host must explicitly initialize the SDK and enable it, and screenshot or semantic-text collection additionally requires a host capture policy naming an eligible surface. The host is expected to complete its own privacy review before enabling collection.

3.2 What a report can contain

Only when a host enables collection and a user opens the reporter:

  • User-written report content — title, description, expected and actual behavior, and optional reproduction steps.
  • Build provenance — package name, version name and code, build variant and an optional commit identifier supplied by the host.
  • Device and window metadata — API level, manufacturer and model, window size, density, locale, font scale and orientation. No unique device identifier.
  • Optional screenshot and semantics — only for surfaces the host policy marks eligible, and only if the user proceeds with the report flow.
  • Optional host evidence — allowlisted breadcrumbs, structured logs, and OkHttp request metadata limited to method, status, timing and a safe route template.

3.3 Where the data goes

Captured content stays in the host application's process and, if the user saves a draft, in encrypted app-private storage. Nothing is transmitted by the SDK. Export writes a local file through the Android Storage Access Framework; sharing hands a file to a destination the user chooses. The project is not a party to either action.

4. What is never collected

  • Screenshots or semantic text without an explicit host capture policy.
  • Passwords, editable input values, clipboard contents, SMS, contacts, location, camera or microphone data.
  • Advertising identifiers, device serial numbers or other unique device identifiers.
  • HTTP request or response bodies, cookies, authorization headers, query strings or raw URL paths.
  • Global logcat, heap dumps, database dumps or background screen recordings.
  • Anything at all when the SDK is not initialized, not enabled, or the surface is not eligible.

Protected windows are omitted. The SDK checks FLAG_SECURE before and after capture and treats a raw PixelCopy success as insufficient privacy proof.

5. Desktop tools and MCP

The validator, inspector, viewer and MCP server run locally. They read a parcel you choose and write output only where you direct them. They do not phone home.

The MCP server is read-only and accepts report IDs, not arbitrary paths. Read-only access is not an egress guarantee: your MCP client and its model provider may forward returned content to a cloud service. If evidence must not leave your machine, use a local client and a local model.

6. Retention

  • Drafts default to 72 hours, at most 10 reports and 25 MiB of encrypted storage. The host may configure stricter values.
  • Temporary share copies are best-effort cleaned after 24 hours.
  • User-selected exports are outside the SDK's retention scope. The SDK cannot delete a file after the user saves or shares it, and a shared file cannot be recalled from the recipient.
  • The project retains no report data because it never receives any.

7. Third-party services

The project uses GitHub for source hosting, issue tracking, discussions, releases and private security advisories. If you open an issue, comment, or submit a security report, GitHub processes that content under its own terms and privacy statement, and it is visible to the extent the channel makes it visible.

Never post a real report, screenshot, credential or personal data in a public issue or discussion. Security reports belong in the private advisory channel.

Links from this site to other websites are provided for reference. Those sites are not covered by this policy.

8. Children and sensitive data

The project is developer tooling and is not directed at children. The SDK is not designed to collect data from children, and hosts are responsible for their own age-appropriateness analysis.

Screenshots and free text can contain sensitive information. The SDK does not guarantee perfect detection or redaction. Application-specific testing and a legal and privacy review are required before production enablement.

9. Your choices

  • Use the site without storage. Clearing site data removes the saved theme preference. The site works without it.
  • Decline a report. No capture occurs until a user opens the reporter, and a user can abandon the flow.
  • Review before export. The exact text and flattened image are shown before approval, and changing content invalidates approval.
  • Delete drafts. Drafts can be deleted in the app; they are stored encrypted in app-private storage.
  • Contact the host. Requests about data collected by a host application must go to that application's developer, because the project never receives it.

Because the project does not collect personal data through the SDK or this website, there is usually no project-held record to access, correct or erase. Where a legal right applies to content you voluntarily posted on GitHub, use GitHub's controls or contact the maintainers.

10. Security

Drafts use AES-256-GCM with an Android Keystore key and are written atomically to noBackupFilesDir. Key or crypto failure returns a typed error; there is no plaintext fallback. The desktop reader treats parcels as hostile input and rejects traversal, symlinks, duplicate entries, oversized JSON and oversized PNGs before rendering.

To report a vulnerability, use GitHub private vulnerability reporting. Do not include real user data. See the security page.

11. Changes to this policy

This policy is versioned with the project and may change as the software or its hosting changes. The effective date at the top of the page is updated when it does. Material changes are recorded in the changelog and the repository history. Because this is a pre-release project, the policy is expected to change before a stable release.

12. Contact

Privacy questions that do not contain sensitive details can be raised in GitHub Discussions. Security-sensitive reports belong in private vulnerability reporting. Do not send personal data, real reports or credentials through any channel.
